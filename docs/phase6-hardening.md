# Phase 6 hardening (0.6.0)

This release adds a first self-hosted hardening slice. It does not claim a complete enterprise security certification or production HA posture. Complete the deployment checklist against the target environment before enabling maintenance.

## Audit integrity and retention

Migration `007_audit_integrity.sql` makes audit rows append-only with PostgreSQL triggers and removes UPDATE/DELETE/TRUNCATE from `PUBLIC`. The runtime-role example also revokes those privileges from `kordex_runtime`. Audit appends serialize on a per-organization chain head and store SHA-256 hashes over a versioned JSON event and its previous hash. Existing rows are retained as explicitly unchained legacy history; the first new event chains from the zero hash and exports include that legacy prefix. The chain detects modification, removal, reordering, or insertion within exported chained records, but it is not a signature and does not stop a database owner from rewriting a whole chain. Audit event IDs are a global PostgreSQL sequence, so gaps between one organization's events are expected and do not indicate tampering.

Configure separate migration and runtime database identities. The Helm migration hook reads Secret key `migrationDatabaseURL`; API and scheduler read `databaseURL`. Use the example grants as a starting point, apply them as the object owner, and validate the effective privileges for your PostgreSQL version and deployment. The migration identity must own/create schema objects; it is not used by steady-state API/scheduler pods.

Export an organization's audit history over HTTPS using `scripts/export-audit.sh`. The script takes a high-water ID, paginates ascending, and fails if a page is empty before that checkpoint or IDs stop advancing. It requires a protected curl config file with no group/other permissions, a dedicated audit signing key, and `kordex-audit-sign`; it writes NDJSON, a SHA-256 sidecar, and a signed checkpoint manifest, then refuses to overwrite any existing artifact. Generate a key pair separate from the maintenance authorization key with `go run ./api/cmd/kordex-keygen -private-file ./audit-signing-private.key -public-file ./audit-trust.json`. Set `KORDEX_AUDIT_SIGNING_KEY_FILE=./audit-signing-private.key` and, when the signer is not on `PATH`, `KORDEX_AUDIT_SIGNER=./bin/kordex-audit-sign`. Protect the private key with mode 0600 and distribute the public trust bundle independently. Verify with `kordex-audit-verify -input export.jsonl -checkpoint export.jsonl.manifest -trust-bundle ./audit-trust.json -through-id CHECKPOINT`. The signed checkpoint binds the organization, high-water ID, record count, exact NDJSON digest, and creation time. Hash chains are checked where present; signed legacy unchained history is still digest-authenticated. Compare the checkpoint with an independently retained high-water record and store the export, manifest, and trust bundle in an independently administered immutable/WORM destination with retention and access logging. `bash scripts/test-export-audit.sh` now builds a temporary key pair, exercises pagination, verifies the signed checkpoint, tests tamper rejection and no-overwrite behavior against a mocked API; this is a local contract test, not evidence of external immutable retention.

The dashboard can also download a bounded `kordex-audit-export-v1` JSON bundle. Verify its embedded digest and hash chain with `kordex-audit-verify -bundle -input export.json -through-id EXTERNALLY_RETAINED_EVENT_ID`. The external checkpoint must come from an independently retained manifest or system; the bundle's own checkpoint cannot prove that its tail was not removed. Browser exports are limited to 100,000 records and 64 MiB of NDJSON. Use `scripts/export-audit.sh` for larger tenant audit archives.

Authenticated membership and role denials are stored in a separate append-only platform chain; unauthenticated credential failures remain in structured application logs. Generate a dedicated audit signing key pair, separate from the maintenance authorization key, with `go run ./api/cmd/kordex-keygen -private-file ./audit-signing-private.key -public-file ./audit-trust.json`. Protect the private file with mode 0600 in the deployment secret store and distribute the public trust bundle independently. Set `KORDEX_AUDIT_SIGNING_KEY_FILE=./audit-signing-private.key` and `DATABASE_URL` to the runtime database connection, then run `kordex-security-audit-export -output ./security-audit.json`. It reads a fixed high-water snapshot, verifies each chain link while paging, signs the manifest (including tenant, fixed checkpoint, timestamp, and record digest) with Ed25519, writes a mode-0600 `kordex-audit-export-v1` bundle, and refuses to replace an existing file. The exporter caps bundles at 100,000 records and 16 MiB of NDJSON. Verify with `kordex-audit-verify -bundle -input ./security-audit.json -trust-bundle ./audit-trust.json -through-id CHECKPOINT`; the trust bundle and checkpoint must be retained independently of the database and export. An unsigned platform-security bundle or untrusted key is rejected. Store the export and its independently retained manifest/checkpoint in an independently administered immutable destination. This file-based signing key is not KMS-backed and its rotation/custody process has not been qualified.

The dashboard's **Export audit snapshot** action calls the tenant-scoped API endpoint, which fixes the high-water ID, validates record ordering and any hash chain, and signs a bundle with the same dedicated audit key. The server rejects snapshots over 4 MiB of NDJSON; use the CLI exporter for larger archives. Helm keeps this download disabled unless `auditExport.enabled=true`; when enabled, the configured credentials Secret must include `auditExport.secretKey` (default `auditSigningKey`). The Kustomize hub API mounts that key at `/var/run/kordex/auditSigningKey` and therefore requires the same Secret item. The key is mounted only into the API, with a pod-specific fsGroup and read-only secret volume. The browser does not validate signatures; verify a downloaded bundle with `kordex-audit-verify -bundle -input FILE -trust-bundle ./audit-trust.json -through-id CHECKPOINT`. No deployed browser/API export or key-custody qualification has been performed.

## Backup and restore

`scripts/backup-postgres.sh` creates a mode-restricted PostgreSQL custom archive using a libpq service file. It rejects a service file readable by group/other users, validates archive readability, and publishes a uniquely named archive and portable SHA-256 sidecar without replacing earlier files; the manifest is published last as the completion marker. Protect the service file with mode 0600 and supply credentials through the platform's secret mechanism. Replicate encrypted backups off-site under a documented retention policy. The script does not configure continuous archiving or point-in-time recovery.

Run `scripts/restore-drill.sh` against a newly provisioned isolated target service. It resolves the archive and checksum sidecar together, verifies the checksum, refuses a target with the same or unknown PostgreSQL server endpoint as the source, refuses targets that already contain user relations, restores without dropping objects, and compares every restored migration version and SHA-256 checksum with the complete contiguous migration set in this checkout. `make test` and CI exercise backup permission/collision/cleanup guards plus same/unknown-server, nonempty-target, stale/incomplete history, checksum mismatch, and successful isolated-target paths with command doubles. Record the drill date, source backup, target isolation, restore duration, row counts, and application-level verification results. These guard tests are not a real PostgreSQL restore drill or evidence of production recovery. Configure and validate PITR separately if required by the service RPO/RTO.

## API protection and metrics

API authentication now applies a token-bucket limit keyed by the verified OIDC subject or isolated bootstrap subject. Defaults are 20 requests/second with a burst of 600; configure `KORDEX_API_RATE_LIMIT_RPS` and `KORDEX_API_RATE_LIMIT_BURST` (Helm: `apiRateLimitRPS`, `apiRateLimitBurst`). Rejections use HTTP 429 and `Retry-After`. The limiter is process-local, so it is not a global tenant quota and the effective allowance grows with API replicas. Agent signed routes do not use user-subject limits. Put global controls at the trusted ingress/API gateway and set agent ingress quotas there; do not key limits to untrusted forwarded IP headers.

Prometheus text metrics are served on a separate listener at `KORDEX_METRICS_LISTEN_ADDRESS` (default `127.0.0.1:9090`). In the control-plane chart they remain loopback-only unless `metrics.enabled=true`, which exposes a separate ClusterIP Service and an ingress NetworkPolicy. NetworkPolicies are additive and depend on the installed CNI. Review `metrics.namespaceSelector` and the cluster's namespace labels; scrape only from a trusted monitoring namespace and do not publish the metrics Service through public ingress. Current metrics cover HTTP request count and latency with bounded labels; they do not yet report scheduler progress, queue age, retained reservations, blocked reasons, or recovery duration.

## Availability and deployment boundaries

The API and scheduler are separate replicated workloads and campaign claims are database-coordinated. This is not a measured HA/SLO claim. Validate database failover, backup recovery, ingress TLS, OIDC provider outage behavior, key rotation, and multi-replica campaign behavior in the target environment. The database remains a required central dependency. Agents continue to enforce local authorization and safety while disconnected; a disconnected cluster must not begin new authorized disruptive work.

Still outside this slice: PostgreSQL RLS, complete denied-access audit coverage, external immutable-retention provisioning, KMS-backed signing, release image signing/provenance, air-gapped artifact bundles, GCP Terraform/Cloud Run deployment, SLO alert rules, and measured production scale. No credentials or cloud resources are provisioned by these scripts or charts.

## Operator checklist

1. Configure HTTPS ingress and OIDC issuer/audience; test tenant isolation and role mapping.
2. Create separate least-privilege database migration/runtime roles and verify runtime cannot mutate audit rows or schema history.
3. Enable TLS verification for database connections; store both URLs and signing keys in the deployment secret manager.
4. Enable an authenticated, private metrics scrape path and configure gateway rate limits for users and agents.
5. Schedule encrypted backups and off-site immutable audit exports; alert on missed backup/export jobs.
6. Perform a restore drill against an isolated target and retain measured RPO/RTO evidence.
7. Validate agent trust rotation/revocation, network partitions, and campaign recovery before authorizing maintenance.
8. Review security advisories, image provenance, and the remaining hardening gaps listed above.
