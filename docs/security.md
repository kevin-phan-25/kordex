# Security model

See the [threat model](threat-model.md) for trust boundaries, attack
scenarios, implemented mitigations, and remaining qualification risks.

## Implemented controls

The service verifies OIDC issuer, audience, signature, allowed algorithms, authorized party and token expiry. OIDC subject identifiers must be 1–255 printable ASCII bytes; empty, non-ASCII, and control-character subjects are rejected before membership lookup or audit attribution. Subjects remain opaque and case-sensitive. The compatibility default uses ID tokens; opt-in RFC 9068 access-token mode also checks JWT type, exact API audience, issue time, subject, OAuth client ID, token ID and configured scopes. Organization membership and viewer/operator/approver/administrator roles are read from PostgreSQL on every request. Each OIDC-authenticated API request also checks the SHA-256 digest of its exact bearer token against the durable revocation registry; registry errors fail closed. Dashboard logout asks the API to revoke that token until its verified expiry, then clears the local cookie. If the API cannot confirm revocation, the cookie is still cleared and the login page reports the incomplete revocation. This revokes the credential at Kordex only; other resource servers and the identity provider may have separate revocation semantics. The dashboard does not obtain refresh tokens or silently extend sessions; users sign in again when the verified bearer token expires. OIDC listeners never accept bootstrap credentials; combining OIDC with the local-development flag fails startup. Isolated non-OIDC loopback/local-development mode retains the global bootstrap token for initial provisioning. The dashboard uses authorization-code flow with PKCE, an encrypted authenticated session cookie, origin validation on mutations, and an organization-scoped, allowlisted server API proxy with streaming byte limits. The cookie key must be random, at least 32 bytes, and shared across dashboard replicas. Production dashboard URLs require HTTPS; insecure cookies are permitted only for loopback development outside production. The exact token contracts and their remaining provider qualification are documented in [the platform security boundary](KORDEX-SECURITY-MODEL.md).

Agents use per-cluster Ed25519 identity over verified HTTPS, single-use enrollment tokens, persisted replay nonces, 24-hour key expiry, restart-safe rotation and transactional revocation fencing. See agent-protocol.md for exact assumptions, including one configured trusted OIDC issuer and membership migration on issuer changes. No agent or Kubernetes credentials are exposed through inventory endpoints.

The API itself serves HTTP behind a trusted TLS terminator. Database TLS requires verify-full outside local mode. Signed agent requests must arrive through HTTPS ingress; clients reject insecure origins outside explicit loopback tests and never forward identity across redirects. Local Compose binds exposed ports to loopback and requires generated secrets.

Requests have bounded bodies, strict JSON fields, UUID validation, bounded pagination and deadlines. SQL is parameterized. Metadata mutations and identity lifecycle events share transactions with audit writes. Request IDs and safe SQLSTATE/category diagnostics are logged, without raw credentials, SQL errors or bodies. Authentication and authorization denials emit structured warning records with a fixed reason code, route pattern, request ID, and authenticated actor when available; valid organization IDs are recorded as attempted targets, never as authority. Credentials, query strings, and request bodies are excluded. Authenticated membership and role denials are also written to a separate append-only, hash-chained platform security stream. The bounded platform-security export, CLI tenant archive, and dashboard download endpoint use Ed25519 signatures; offline verification requires a separately supplied public trust bundle. The dashboard API signs a fixed tenant high-water snapshot after validating its ordering and hash chain, and refuses exports above its 4 MiB NDJSON bound. The browser checks the returned digest and tenant binding but does not verify the signature; use `kordex-audit-verify -bundle` before relying on it. Anonymous credential, malformed-target, and rate-limit failures remain log-only to avoid unauthenticated or high-volume database write amplification. The signing key is file-based, not KMS-backed, and custody/rotation plus independent immutable retention have not been qualified. Audit actor attribution distinguishes OIDC from bootstrap administration. Tenant audit chains continue to cover successful organization-scoped metadata changes and identity lifecycle events.

The agent Helm chart has separate resource-limited RBAC, no host mounts or maintenance privileges, nonroot/read-only containers and retained identity storage. Enable Kubernetes Secret encryption at rest and protect Helm release storage, which may include the retained identity Secret. Hub Helm charts provide opt-in ingress and per-component egress policies. Agent and operator Helm charts also provide opt-in, explicitly peer-scoped egress policies with validated numeric ports. Configure all site-specific dependencies and verify CNI enforcement; spoke Kustomize overlays still require site-authored policies.

Phase 6 adds database-level append-only triggers for audit rows, versioned per-organization audit chains, a separate global security-denial chain, export verification, and backup/restore helper scripts. Audit event IDs come from PostgreSQL sequences, so gaps are valid; verification checks ascending IDs, each previous-hash link, and the independently retained final checkpoint instead of requiring adjacent IDs. Existing tenant audit records remain unchained. Platform security exports additionally bind the checkpoint and record digest in an Ed25519-signed manifest; the verifier requires an independently distributed trust bundle for those exports. Use the separate migration and runtime database URLs in the control-plane chart and apply the example runtime grants from `deployments/local/postgres-runtime-grants.sql` as a starting point. These controls are not proof of a completed backup restore or immutable export. A database owner can still rewrite rows and recompute a chain, and a signature is only as trustworthy as key custody and independent retention. See [Phase 6 hardening](phase6-hardening.md).

## Required production model

Use OIDC issuer/JWKS validation with issuer, audience, expiration and algorithm restrictions, key rotation, bounded cache freshness and explicit failure behavior. Map immutable subject IDs into organization memberships and roles: viewer, operator, approver and administrator. Define approval separation of duties. Authorization must apply to every resource and query; caller-supplied organization IDs never confer membership. Test cross-tenant reads/writes and aggregate endpoints. Add PostgreSQL row-level security as defense in depth once verified transaction-scoped identity propagation is designed.

Agents enroll with short-lived one-time enrollment tokens bound to an organization and cluster. Rotatable signed HTTPS identity is implemented; mTLS is an optional future deployment model. Verify expiry, revocation and immutable cluster identity server-side. Never bake secrets into images. Disconnected/expired/revoked identities cannot begin disruptive work. TLS root rollover and production identity recovery drills remain deployment gates. Agent key rotation and server-side revocation are implemented.

Dashboard obtains only management API credentials. It never receives kubeconfigs, node credentials or agent keys. The dashboard sets secure, HTTP-only, same-site cookies in production, checks request Origin on state-changing proxy/logout requests, and sets a restrictive content policy. The API remains the authorization authority. Secrets come from mounted secret files or Secret Manager using workload identity; environment secrets in local Compose are development convenience only.

Operator and agent service accounts get separate least-privilege RBAC. No wildcard cluster-admin role. Node patches, pod evictions, node reads, specific CRDs/status updates and leader election permissions must be justified individually. Host package/reboot execution requires a reviewed privilege boundary, action allowlist, identity verification and immutable operation ledger. No arbitrary remote shell command API.

CI scans Go vulnerabilities, containers and frontend dependencies, and is configured to generate CycloneDX SBOM artifacts bound by checksum to the source commit and built image config digest, with 30-day artifact retention. All four runtime Dockerfiles use digest-pinned base image indexes, and CI checks that lock. Production Helm profiles for all four application charts require immutable SHA-256 image references; regular chart values remain tag-compatible for development.

All dashboard-to-management API requests use manual redirect handling; the catch-all proxy returns an error on redirect instead of following a changed target. The `ci.yaml` workflow has a manually dispatched release path. It requires selecting an existing `vMAJOR.MINOR.PATCH` tag and separately setting `publish_images=true`; it waits for every current CI job, builds temporary multi-platform candidate images, scans the exact candidate digest, generates and validates a CycloneDX SBOM, publishes GitHub provenance and SBOM attestations, keylessly signs that digest with Cosign, and only then adds the version tag. It fails closed if the registry cannot establish whether the tag is unused, checks that the final tag resolves to the signed digest, and retains per-image digest/SBOM evidence. Deployments must use the recorded digest because the registry version tag itself is mutable. The workflow is configured but has not been dispatched; no Kordex release signature, provenance, or release SBOM has been independently verified. An opt-in Kyverno ClusterPolicy now verifies digest-pinned signatures from the exact Kordex release workflow identity; it is not installed or qualified against a live admission controller, and provenance/SBOM attestations are not yet admission-enforced. Secret scanning and least-privilege cloud deployment identities also remain pending.

The offline release bundle has detached Ed25519 signing, independent verification, image digest locks, and private-registry delivery instructions; operators still need to manage trusted key distribution, private registry credentials, TLS, and offline OIDC. The bundle signature authenticates release files and does not replace container signature/provenance attestations. No GCP resources or credentials are created by the local development setup.

## Maintenance authority (0.3.0)

An optional hub Ed25519 signing key grants only the two implemented action types against fixed cluster/node/policy identities for fifteen minutes. Its private key never enters a managed cluster. A separately provisioned public trust bundle and a 45-second agent-published connection Lease are required by the local operator. Slow preflight work cannot extend a grant: identity, cancellation, policy, node health, slot and expiry are rechecked immediately before disruptive effects.

The agent may create immutable operation inbox resources and patch acknowledgements; it cannot write their status, patch nodes, delete pods or create evictions. The operator has explicit node-patch/eviction permissions but no Secret-read, pod-delete, host execution or privileged-container capability. Durable receipt/slot state lives in a dedicated namespace and cannot be expired to bypass unavailable capacity. Terminal CRs remain protected until central audit/status acknowledgement. See maintenance-operator.md for the constrained safety contract and remaining production hardening.

Namespace administration, operator deployment/trust configuration and the Kubernetes control plane are trusted boundaries. The platform cannot defend against a cluster administrator deliberately removing finalizers or modifying coordination state. Network partitions have bounded detection latency, not instantaneous detection. Clocks must be synchronized within five seconds.

## Phase 4 campaign controls

Organization roles now include operator and approver. Approval rejects every actor who created, edited or started the plan and binds digest/generation/stage/epoch. Safety resumes require explicit failure acknowledgment after all active work recovers. Signed exact-command withdrawals stop disruption without granting authorization. Shared reservations cover manual and campaign work; no timeout force-releases offered operations. See [campaigns](campaigns.md) for upgrade ordering, bootstrap and deployment prerequisites.
