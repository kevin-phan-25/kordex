# Kordex Ansible Execution Environment catalog

The EE contains two fixed host-upgrade catalogs: Debian/Ubuntu (`kordex.os-upgrade.debian.v2`) and RPM-family DNF (`kordex.os-upgrade.rhel.v1`). The DNF catalog accepts the listed RHEL-compatible distributions and Amazon Linux 2023; Amazon Linux 2 and AL2027 Preview are rejected. Amazon Linux 2023 uses the provider-neutral SSH/DNF path and needs no AWS API access. This support is not production-qualified until its own disposable EKS/VM recovery drills pass. Every accepted host policy must use `actionMarkerVersion: 1`; markerless legacy plans and EE builds are rejected. Policy schema v1 uses the host's configured package repositories. Schema v2 selects `artifactMode: OfflineArtifacts`, requires a SHA-256 for every `.deb`/`.rpm`, verifies the root-owned file at `/var/cache/kordex/artifacts/<sha256>.deb` or `.rpm` during preflight, verifies embedded package identity/version, and invokes the package manager with repository/download access disabled. Package dependencies must also be listed and staged; the operation fails before cordon if an artifact is absent or mismatched. Stage artifacts on each worker before creating the operation. The root-owned host journal binds apply/reboot intent and verified outcomes to the operation, plan, node, machine, and boot identities. It is an execution artifact, not a general Ansible interface: the operator passes a bounded JSON plan, target IP, machine/node identity, and a signed plan digest. The image contains both fixed playbooks and one entrypoint; callers cannot provide playbook text, inventory, tags, or command arguments.

## Build an EE image

Choose and review an Ansible Execution Environment base image, then pin its OCI digest. The build verifies and embeds the base image reference, Ansible runtime version, playbook digest, and collections-lock digest in image labels and the fixed catalog. At runtime, the entrypoint rechecks the catalog files and installed Ansible version. Do not use a mutable tag for the base or publish the final image without pushing it to a registry and recording its resulting digest.

```bash
export KORDEX_ANSIBLE_EE_BASE='registry.example/ansible-ee-base@sha256:REPLACE_WITH_64_HEX_DIGEST'
export KORDEX_ANSIBLE_EE_TAG='registry.example/kordex/ansible-ee:build-1'
./integrations/ansible-ee/build-ee.sh
podman push "$KORDEX_ANSIBLE_EE_TAG"
podman image inspect "$KORDEX_ANSIBLE_EE_TAG" --format '{{.Digest}}'
```

Use the final registry reference with its `@sha256:` digest as `UpgradePolicy.executionEnvironment`. The fixed catalog JSON records each playbook digest separately; use the digest for the selected catalog and the shared `collectionsDigest` in the signed policy. Debian uses exact APT package versions; RHEL uses complete RPM EVR pins (optional epoch plus version and nonempty release) with DNF. A version-only RHEL pin is rejected by both the shared policy validator and the EE entrypoint. The OS family and catalog ID must match. Kernel packages require an explicit reboot policy and `expectedKernelVersion` pinned to the exact expected `uname -r`; the EE receipt and operator verify it before recovery can uncordon the node. For RHEL policies using `IfNeeded` or `Never`, the target must also provide `dnf needs-restarting -r`; the playbook checks for a clean baseline before mutation and checks again after package installation, with all repositories disabled. Missing or indeterminate reboot evidence blocks the operation. Hooks and local retries remain unsupported.

## Cluster-side prerequisites

The cluster operator creates one immutable request ConfigMap and one Kubernetes Job per operation phase. The Job uses an image digest that must be present in the operator's `KORDEX_UPGRADE_EE_ALLOWLIST`, then runs a fixed `/usr/local/bin/kordex-upgrade` entrypoint. Policy authors cannot select arbitrary images even when they provide a digest. The Job has no Kubernetes API token and no host mounts. The entrypoint passes Ansible an explicit minimal environment, so inherited `ANSIBLE_*`, Python module path, SSH agent, and other pod environment overrides cannot change the fixed playbook invocation. It requires:

* A `kordex-upgrade-runner` ServiceAccount with token automount disabled and no RoleBindings.
* A fixed SSH Secret containing only `id_ed25519` and a fixed ConfigMap containing only `known_hosts`, with host keys pinned under the Kubernetes node names.
* The operator's preconfigured SSH user, not supplied by the campaign or policy.
* Optional `KORDEX_UPGRADE_IMAGE_PULL_SECRETS` names for namespace-local registry credentials when node-level image pull identity is unavailable. The referenced Secrets are used only by the Kubernetes image pull path; they are not mounted into the EE container.
* A CNI that enforces Kubernetes NetworkPolicy. Before activating an EE Job, the operator creates a policy selecting only that Job's pods, denies ingress, and allows egress only to the signed target IP on TCP/22. Since Kubernetes combines policy allows, the operator refuses to run when another standard NetworkPolicy both selects the EE pod and has egress allow rules. Audit CNI-specific policy resources and prevent them from widening EE access; standard NetworkPolicy inspection cannot detect vendor policy CRDs. Policy drift blocks execution, and the Kordex policy remains until the Job's pods stop. Configure routing and firewall rules for this path as well.
* A node SSH account with the required narrowly controlled become privileges.

The runner enforces SSH host-key checking with `HostKeyAlias` set to the validated Kubernetes node name; only the mounted `known_hosts` file is trusted, and SSH does not perform a separate IP-key lookup. The operator accepts only a unicast node IP and rejects loopback, unspecified, multicast, and link-local destinations. Populate `known_hosts` with entries keyed by node name, for example `worker-01 ssh-ed25519 AAAA...`; obtain and approve those keys through trusted host provisioning or console access. Each node must have a unique SSH host key; do not clone host private keys from a VM image. Do not use an empty or wildcard entry, or trust an unverified `ssh-keyscan` result. Replacing a node's SSH host key requires an explicit reviewed ConfigMap update. On a signed cancellation, the operator first checks for an already persisted verified receipt. It accepts that receipt only to enter local recovery and never starts a later package/reboot phase. Otherwise cancellation writes an immutable operation/phase tombstone and requests Job deletion; retries cannot recreate that Job. Because Job deletion cannot prove a remote playbook stopped, the operator persists a separate read-only inspection Job to verify package pins and host identity before recovery. Missing or inconsistent inspection evidence keeps the reservation and cordon until intervention.

The EE entrypoint runs Ansible and its local SSH children in a dedicated process group. On pod termination or timeout it forwards termination, waits briefly, and kills remaining local processes before exiting. A remote package-manager process can still outlive a lost SSH connection; Kordex reports that outcome as ambiguous and keeps the node fenced for read-only inspection or intervention. Failed Jobs expose only a fixed final-line `KORDEX_EE_ERROR` code through Kubernetes termination status; the Ansible transcript itself is not copied into operation status. Host-key, SSH-authentication, SSH-transport, timeout, and interruption outcomes have separate reasons.

Before package mutation and reboot, and after each verified marker transition, the playbooks run GNU `sync --file-system` against the root-owned marker directory. This asks the host to flush the journal transition and directory metadata before the next lifecycle step. It improves crash-recovery evidence but is not a power-loss durability guarantee across every filesystem, controller, or storage cache; qualify it on each supported OS and storage stack.

## Supported behavior and limits

Preflight reads distribution family, `/etc/machine-id`, and boot ID. Repository-backed schema v1 resolves each exact package pin in Ansible check mode using the existing APT cache or DNF metadata; it does not refresh metadata. Offline schema v2 verifies each staged artifact's digest and package identity, then simulates the Debian transaction with APT downloads/removals disabled or runs an RPM transaction test with all DNF repositories disabled. Before the DNF test, `rpmkeys --checksig` requires each local RPM to verify against the host's existing offline RPM keyring; DNF local-package signature checks remain enabled in both test and apply. DNF `obsoletes` processing is explicitly disabled for both the transaction test and apply, preventing RPM obsoletes metadata from expanding the package plan through removals. Kordex never imports package keys as an operation side effect. This checks the requested package set and dependency closure before cordoning without applying packages or accessing a repository. Include every dependency not already installed as an explicit pinned artifact. Apply for schema v1 leaves metadata refresh disabled and uses the configured repository; keep local metadata current and use approved internal mirrors. Schema v2 apply passes only the verified local package files and disables repository/download access. Debian and RHEL package-manager tasks prohibit removals, downgrades, weak/recommended dependencies, and disabled signature checks. The EE verifies exact installed Debian versions or RPM epoch/version/release, and records the policy's canonical package pins in the receipt. `IfNeeded` considers kernel package selection on both families and Debian's `/var/run/reboot-required` marker; RHEL relies on the pinned kernel-package plan. The EE recomputes the canonical plan digest and rejects tampering. If a reboot is required, the operator persists that evidence and authorizes a separate immutable reboot request. The deterministic reboot Job checks machine continuity, changed boot ID, expected kernel, and exact package state. `Never` rejects kernel package plans. Neither playbook changes repository configuration or runs arbitrary hooks.

When an apply or reboot outcome is ambiguous and no verified execution receipt exists, the operator may run a separate fixed `inspect` phase. It is read-only: it checks the exact pinned versions, machine ID, and current boot ID, and reports whether a reboot remains required. The operator persists the deterministic inspection reference before starting it and snapshots the known-hosts data into an immutable, operation-owned ConfigMap. A matching inspection allows only the existing node/workload recovery process to continue; it never retries package installation or reboot. Missing or mismatched package/identity evidence keeps the operation cordoned for intervention. After a host-key verification or SSH-authentication failure, an administrator may update the pinned known-hosts ConfigMap or SSH Secret; the operator hashes both inputs into the next attempt identity and starts a new immutable inspection attempt only when that digest changes. The SSH key itself stays in the configured Secret and is never copied into the checkpoint or inspection request. The old attempt and its known-hosts snapshot remain intact. SSH transport failures remain blocked for operator intervention because a transient network change is not represented by either input digest and must not cause an automatic retry loop.

The adapter is wired into the maintenance controller behind `KORDEX_ENABLE_HOST_UPGRADES` (false by default). A verified EE receipt is copied to a deterministic immutable ConfigMap so status recovery does not depend on retaining Job Pod logs. Both catalogs still require disposable VM upgrade, reboot, interruption, and recovery qualification; keep the gate disabled outside that lab. GKE Container-Optimized OS is not supported by either host package catalog and requires the optional GKE node-pool adapter.
