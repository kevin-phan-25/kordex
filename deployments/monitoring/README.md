# Prometheus and Grafana examples

Enable the control-plane chart's private metrics Service (`metrics.enabled=true`) and configure its namespace selector to permit only the trusted monitoring namespace. The metrics listener is HTTP and has no application authentication; network policy, namespace RBAC, and private cluster networking are its security boundary. Never route it through public ingress. CNI NetworkPolicy behavior must be validated in your cluster.

The API Service has Prometheus scrape annotations. With campaign metrics enabled, the scheduler exposes its own private Service and the operator chart can expose local recovery metrics. Configure Prometheus to discover annotated Services in the Kordex namespace, or use your Prometheus Operator's `ServiceMonitor` with namespace and release labels appropriate to your cluster. Apply both `prometheus/kordex-alerts.yaml` and `prometheus/kordex-operations-alerts.yaml` only after matching their `release` and namespace labels and reviewing thresholds against observed traffic.

Import `grafana/kordex-overview.json` for API request rate, 5xx rate, and latency. Import `grafana/kordex-operations.json` for due queue age, active and oldest reservation, active RecoveryRequired count and oldest age, recovery snapshot completeness, terminal operation outcomes, verified drain/reboot/terminal duration, blocked operation reasons, recovery safety blocks, and completed recovery duration. Import `grafana/kordex-fleet.json` for aggregate cluster connectivity, node readiness, oldest heartbeat/inventory age, and the scheduler snapshot age. The scheduler refreshes durable fleet and queue gauges every 15 seconds when its metrics listener is enabled; a missing snapshot timestamp means no successful snapshot has been exported. When multiple scheduler replicas are scraped, these cluster-wide snapshots are duplicated, so dashboard queries use `max`, not `sum`. The operator refreshes aggregate active-recovery gauges every 15 seconds from the Kubernetes API under leader election. Snapshot success, timestamp, and completeness metrics let alerts distinguish stale data and invalid/missing durable `recoveryStartedAt` values; losing leadership marks that replica's snapshot inactive, and dashboard/alert expressions select only successful snapshots. The operator also exports `kordex_operator_maintenance_transitions_total`, `kordex_operator_maintenance_blocked_total`, `kordex_operator_maintenance_phase_duration_seconds`, bounded terminal outcome and duration histograms, and a separate RecoveryRequired counter. Drain samples cover the durable `Draining` phase through verified drain completion; reboot samples cover `Rebooting` through verified host reboot evidence; terminal operation duration begins at the first durable phase event. Scheduler logs and `kordex_scheduler_errors_total` use bounded `error_class`/`class` values and omit database messages. These are operational signals, not approved SLOs. Recovery-duration histograms include completed recoveries only; blocked operations remain visible through the scheduler snapshot and bounded block counters. Metric labels deliberately omit organization, cluster, node, operation, and user identifiers; unknown action/phase/reason/outcome labels map to `other`. The four-hour reservation alert is an operator prompt, not a timeout or permission to release a safety reservation. Validate this threshold against configured operation timeouts before enabling the alert.

Enable `metrics.enabled=true` on the control-plane Helm chart to expose API and scheduler metrics through private ClusterIP Services. Enable the same option on the operator Helm chart to expose its metrics. Both charts default to loopback-only metrics; when enabled they bind to the pod interface and install an ingress NetworkPolicy limited to `metrics.namespaceSelector`. Validate these policies with the cluster CNI and keep the Services off public ingress.

The API, scheduler, agent, and maintenance operator create OpenTelemetry spans. Set Helm `telemetry.otlpEndpoint` or the component's Kustomize `otelExporterOtlpEndpoint` setting to an explicitly approved OTLP/HTTP collector; empty defaults disable export. Helm schema and application startup validation reject credentials, query strings, fragments, unsupported schemes, and missing hosts in endpoint URLs. API spans include route templates, bounded methods, status, and duration; scheduler spans include bounded outcome/error class and admitted count; agent spans use allowlisted routes and propagate W3C context to the hub; operator spans include bounded phase/action/outcome and normalized error class. Spans omit request payloads, raw URLs, customer/operation/node IDs, SQL text, and raw errors. If restricted egress is enabled, add only the collector peer and required port to each component's NetworkPolicy. Keep collector transport private and TLS-protected outside an isolated local test. All four services currently sample at 10%; validate collector load and retention before production use.

Both the dashboard and alert thresholds require validation with the installed Prometheus/Grafana versions, scrape interval, traffic volume, and organizational SLOs. No monitoring stack is installed by the Kordex Helm charts.
